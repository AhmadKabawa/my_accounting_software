# CAT-07 — البيانات الأساسية ومواصفة الماركات

- **الرمز:** CAT-07
- **العنوان:** البيانات الأساسية — الماركات والتصنيفات وأنواع المنتجات
- **النطاق التنفيذي الحالي:** الماركات هي التبويب الوظيفي الوحيد في هذا الفرع؛ `/catalog/master-data` مسار توجيه فقط إلى `/catalog/brands`. لا يُبنى غلاف تبويبات أو صفحة مركز أو TabBar أو registry للتبويبات الآن. التصنيفات وأنواع المنتجات توسعات لاحقة بمواصفات مستقلة.
- **الحالة:** معتمدة 2026-11-20
- **المسار القائم:** /catalog/brands
- **المراجع الأساسية:** S49 في scenarios/03_catalog_pricing.md، ERP_Screen_Navigation_Map §4.4، DATA_MODEL، A4_decisions_log، FEATURE_TEMPLATE، ARCHITECTURE_RULES، DESIGN_SYSTEM وADR-0003.
- **قرارات المستخدم:** D-01: `/catalog/master-data` مسار توجيه فقط إلى `/catalog/brands` مع إبقاء المسار الفعلي ورابطه المباشر؛ لا غلاف تبويبات حتى تنفيذ التبويب الثاني. D-02: لا تظهر التصنيفات وأنواع المنتجات في هذا التسليم. D-03: اعتماد بقية المواصفة كما هي، مع تحديث S-01 بقرار D-05، وعدد المنتجات الثانوي، وضوابط الحذف والإيقاف، والبحث والفرز والنموذج وخريطة الأخطاء وترتيب التنفيذ. D-04: الإضافة السريعة من نموذج المنتج تحتاج عقداً عاماً لاحقاً بسبب ADR-0004، وتبقى مفتوحة دون تنفيذ. اعتماد Ledger Design System وAppDensity كما هما.

> هذه المواصفة لا تنشئ حقولاً أو قواعد عمل جديدة. أي بند لا يسنده السيناريو أو نموذج البيانات أو القرار المعتمد موسوم بأنه اقتراح أو قرار يحتاج موافقة.

## 1. معلومات الشاشة

CAT-07 نطاق بيانات مرجعية يحتاجها إنشاء المنتج. سيناريو S49 يحدد كيانات الماركات والتصنيفات وأنواع المنتجات؛ لكن هذا الفرع ينفذ الماركات فقط. خريطة التنقل توسّع الرؤية المستقبلية إلى الألوان وأنظمة المقاسات والوحدات والجداول الوصفية والخصائص والخيارات وربط النوع بالمقاسات والخصائص.

**قرار النطاق لهذه المرحلة:** الماركات هي التبويب الوظيفي الوحيد في هذا الفرع. `/catalog/master-data` مسار توجيه فقط يعيد إلى الصفحة الفعلية `/catalog/brands`. لا توجد صفحة مركز أو غلاف تبويبات أو TabBar أو registry للتبويبات الآن. التصنيفات وأنواع المنتجات لا تظهر في هذا التسليم؛ فكل منهما توسعة لاحقة تحتاج مواصفة مستقلة. بقية مجالات خريطة التنقل تبقى توسعات لاحقة، ولا تظهر كعناصر وهمية بلا تنفيذ.

المسار القائم `/catalog/brands` هو الصفحة الفعلية والرابط المباشر الصالح. المسار `/catalog/master-data` مسار توجيه فقط يعيد إلى `/catalog/brands`؛ لا ينشئ صفحة أو غلافاً أو تبويبات في هذا الفرع. يُعرّف المسار في `catalog_routes.dart` ضمن `all` ويُسجل مع مجموعة الحراس نفسها لمسار الماركات، بعد التحقق من عدم تعارضه مع `route_registry` و`app_go_router`. يبقى breadcrumb «Catalog ← Brands» دون تعديل توقيع AppBreadcrumb. لا تظهر التصنيفات وأنواع المنتجات حتى تُعتمد مواصفاتهما وتنفذا.

## 2. الهدف والنتيجة

- إدارة الماركات والتصنيفات وأنواع المنتجات التي تعتمد عليها نماذج المنتج.
- جعل شاشة الماركات مرجعاً تأسيسياً لقائمة/جدول ERP: فصل المعمارية، ثبات عقد البيانات، معالجة الأخطاء، الصلاحيات، الحالات، والتجاوب.
- إبقاء تبويبات CAT-07 واضحة ومتماسكة دون خلط مسؤوليات الكيانات.
- النتيجة المقبولة: يستطيع المستخدم المخوّل إدارة الماركات، ويستطيع المستخدم المسموح له القراءة استعراضها، وتكون إجراءات الحالة والحذف آمنة وفق ارتباط المنتجات.

**لماذا لا نبني CRUD عاماً تلقائياً؟** لأن S49 يجمع كيانات مختلفة في مركز واحد، لكن لكل كيان بنية وعمليات مختلفة؛ كما أن الماركة لها شعار وslug وعلاقة منتجات، بينما التصنيف شجري ونوع المنتج يرتبط بالمقاسات والخصائص. لذلك يكون المركز غلاف تنقل، وتبقى كل تبويبة مسؤولة عن سلوك كيانها.

## 4. المستخدمون والصلاحيات

- **الأدوار المنفذة:** MANAGER وPURCHASER وWAREHOUSE.
- **صلاحية الكتابة:** masterdata.manage.
- **القراءة:** مفتوحة وفق RLS للبيانات الأساسية، وقراءة المنتجات مفتوحة أيضاً.
- **واجهة القراءة:** لا تحجب القائمة عن المستخدم read-only.
- **الإنشاء والتعديل وتغيير الحالة والحذف:** خلف PermissionGate(masterdata.manage).
- **المرجع النهائي للتفويض:** RLS في قاعدة البيانات؛ PermissionGate تحسين عرض فقط.
- **رفض القراءة 403:** حالة Permission Denied مستقلة، لا Empty ولا خطأ عام.
- **سبب الفصل:** S49 يحدد masterdata.manage للكتابة، وDATA_MODEL يثبت read=true.

## 5. السيناريوهات

### S49 — الماركات والتصنيفات وأنواع المنتجات

**الهدف:** إدارة البيانات الأساسية التي تعتمد عليها نماذج المنتج.

**المسار الأساسي:**
1. فتح مركز البيانات الأساسية.
2. اختيار تبويب الماركات أو التصنيفات أو أنواع المنتجات.
3. إضافة ماركة عبر الاسم والمعرّف والوصف والشعار.
4. إضافة تصنيف تحت أب مع الاسم والمعرّف والترتيب.
5. إضافة نوع منتج مع الاسم والرمز والوصف.
6. ربط نوع المنتج بمقاساته وخصائصه وفق S48 وS53.

**المسارات البديلة:**
- الإضافة السريعة من نموذج المنتج وفق S07/S49.
- تعطيل البيانات الأساسية بدلاً من حذف ما استُخدم.

**معايير القبول المرجعية:** slug المكرر يُرفض برسالة مفهومة؛ لا يكون التصنيف أباً لنفسه؛ البيانات الأساسية المحفوظة تظهر في القوائم المنسدلة لنموذج المنتج.

**لماذا الماركات أولاً؟** لأن التكليف يحددها كطيّار الجدول (V1_SCOPE)، ولأنها تملك علاقة مباشرة بـ products عبر brand_id، وتوفر اختباراً عملياً لإجراءات CRUD وحالات الاستخدام والصلاحيات.

## 6. البيانات ومصادرها

### جدول brands

| الحقل | العقد | الظهور | السبب |
|---|---|---|---|
| id | bigint PK | لا يظهر | مفتاح تقني للطلب والصف |
| name | varchar(150), NOT NULL, UNIQUE | أساسي | هوية الماركة |
| slug | varchar(150), NOT NULL, UNIQUE | أساسي/ثانوي بحسب المساحة | معرّف ثابت للربط والبحث |
| logo | varchar(500), nullable | صورة الهوية | S49 يطلب الشعار، والرابط فقط في C19 |
| description | text, nullable | ثانوي | سياق إضافي عند توفره |
| is_active | boolean, default true | أساسي | الحالة التشغيلية |
| timestamps | قياسية | لا تظهر | حقول تدقيق/تقنية |

### علاقة المنتجات

- FK المؤكد: products.brand_id → brands.id.
- RLS للقراءة على brands وproducts = true وفق DATA_MODEL.
- يمكن طلب عدد المنتجات بتضمين PostgREST products(count) باستخدام العلاقة المؤكدة.
- العدد معلومة ثانوية، لا يكون أساس قرار الحذف وحده؛ قيد FK في قاعدة البيانات هو الحكم النهائي.
- لا RPC ولا View ولا migration.

### حقول لا تُضاف
لا موقع رسمي ولا بلد منشأ للماركة ولا أسماء معرّبة ولا مرجع خارجي. هذه غير موجودة في عقد brands الحالي. لا تخلط ملف الماركة بملف المورد/المصنّع.

## 7. المعلومات المعروضة

| العنصر | الأولوية | المصدر | لماذا؟ |
|---|---|---|---|
| الشعار + الاسم + slug | أساسي | brands.logo/name/slug | تعريف بصري ولفظي ثابت |
| الحالة | أساسي | brands.is_active | تمييز السجل النشط عن الموقوف |
| الوصف | ثانوي | brands.description | تفاصيل مساندة لا يحتاجها كل مستخدم |
| عدد المنتجات | ثانوي ومشروط | products(count) | معرفة الاستخدام ومساندة قرار الإيقاف/الحذف |
| id/timestamps | مخفي | قاعدة البيانات | لا تخدم مهمة المستخدم اليومية |

الهاتف يعرض بطاقة تجمع الهوية والحالة والوصف عند توفره وعدد المنتجات عند تفعيله، مع إجراءات الصف في قائمة المزيد.

## 8. الإجراءات

| الإجراء | الصلاحية | العملية | الضبط |
|---|---|---|---|
| إنشاء | masterdata.manage | POST /rest/v1/brands | name, slug, logo, description؛ لا ترسل is_active في الإنشاء، فالافتراضي true |
| تعديل | masterdata.manage | PATCH على id | تحديث الحقول القابلة للتحرير؛ لا تُعدّل الحالة من النموذج |
| إيقاف | masterdata.manage | PATCH ?id=eq.<id> بجسم { "is_active": false } فقط | تأكيد قبل الإيقاف؛ منع التكرار؛ رسالة نجاح |
| إعادة تفعيل | masterdata.manage | PATCH ?id=eq.<id> بجسم { "is_active": true } فقط | دون تأكيد؛ منع التكرار ورسالة نجاح |
| حذف | masterdata.manage | DELETE ?id=eq.<id> | تأكيد صريح باسم الماركة؛ لا يظهر إذا كان product_count أكبر من صفر |
| إعادة المحاولة | حسب سياق القراءة | GET | تظهر في حالة الخطأ |

### قاعدة الحذف والإيقاف
- إذا كان عدد المنتجات المعروف أكبر من صفر، لا تعرض حذفاً؛ اعرض إيقافاً فقط مع توضيح أن الماركة مرتبطة بمنتجات.
- لا تعتمد على العدد وحده؛ قيد FK في قاعدة البيانات هو الحكم.
- إذا فشل DELETE بسبب FK (HTTP 409 أو PostgreSQL 23503)، اعرض حواراً يشرح أن الماركة مستخدمة ويعرض «إيقاف بدلاً من الحذف».
- عند حذف/إيقاف آخر سجل في الصفحة الحالية، ارجع إلى الصفحة السابقة إن كانت متاحة.
- لا تُعد محاولة كتابة فاشلة تلقائياً؛ RetryInterceptor يعيد GET فقط.

## 10. البحث والفلاتر والفرز

- **البحث:** الاسم وslug فقط، كما هو حالياً؛ بحث خادمي، escaping صحيح، debounce 300ms داخل Cubit، وحارس آخر طلب يفوز.
- **فلتر الحالة:** الكل/نشطة/موقوفة. له معنى تشغيلي لأن الإيقاف هو البديل عن حذف الماركة المستخدمة.
- **لا فلاتر أخرى:** لا توجد حقول موثقة تستحق فلاتر إضافية.
- **الفرز:** الاسم فقط. الوصف والشعار والحالة وعدد المنتجات لا تستحق فرزاً في هذه الشاشة؛ لا تغيّر أولوية العمل ولا توجد حاجة موثقة لها.
- **عدد النتائج:** إجمالي النتائج بعد البحث والفلتر، وليس عدد الصفحة الحالية.
- **التفاعل:** كل تغيير يعيد الصفحة إلى الأولى؛ إزالة فلتر الحالة لا تمسح البحث، ومسح الكل يعيد البحث والحالة إلى الافتراضي.
- **الترقيم:** page/pageSize من AppConfig؛ الافتراضي 25 والخيارات 10/25/50/100.

## 11. الجدول والقائمة

1. **الهوية:** شعار + اسم + slug، عمود أساسي.
2. **الوصف:** ثانوي، يختفي على التابلت وما دونه وفق C13.
3. **الحالة:** أساسي، AppBadge.
4. **المنتجات:** ثانوي، يظهر فقط بعد تضمين products(count) المؤكد.
5. **الإجراءات:** تعديل + قائمة المزيد.

الهاتف يستخدم بطاقات عبر cardBuilder الموجود/المعاد تنظيمه، ويعرض نفس المعلومات الأساسية. لا تعرض id أو timestamps. لا تضع density صراحة؛ AppDataTable/AppDensityScope يحددانها.

## 12. النموذج

**الإنشاء:** الاسم، slug، الشعار (URL)، الوصف. لا حقل حالة؛ قاعدة البيانات تجعل is_active=true افتراضياً.

**التعديل:** الاسم، slug، الشعار، الوصف. لا تعديل للحالة من النموذج؛ الحالة عبر إجراء الصف فقط.

**التحقق:**
- الاسم مطلوب وبحد قاعدة البيانات 150 حرفاً.
- slug مطلوب وبحد 150 حرفاً، ويحافظ على قواعد slug الحالية (حروف لاتينية صغيرة وأرقام وشرطة وفق النمط القائم).
- الشعار اختياري، URL من HTTP/HTTPS فقط، وبحد 500 حرف.
- الوصف اختياري؛ لا حد جديد مفترض ما لم يفرضه Core/القاعدة.
- التكرار في name أو slug يعرض رسالة واحدة؛ لا تحلل نص الخادم للتمييز بينهما.
- استخدم AppValidator/ValidationRule؛ لا validator موازياً.

**الشعار:** رابط URL فقط؛ لا رفع ملفات أو Storage في هذا النطاق. المعاينة اختيارية وفق الرابط الصالح.

**التخطيط:** حوار على التابلت/المكتب. على الهاتف استخدم full-screen أو bottom sheet فقط إذا كان Core يوفره؛ وإلا يبقى الحوار الحالي مع توثيق القيد. لا تنشئ مكوّناً عاماً لمجرد هذه الشاشة.

**UnsavedChangesGuard:** لا يُربط في هذه المرحلة؛ يُسجل كبند مفتوح/اقتراح.

## 13. الحالات

| الحالة | تنطبق؟ | السلوك |
|---|---|---|
| Initial | لا | التحميل يبدأ عند فتح الصفحة |

## 14. التنقل بين الحالات

- مركز CAT-07 يجمع التبويبات، والانتقال بين التبويبات لا يخلط حالات كياناتها.
- /catalog/brands يبقى deep link صالحاً إلى تبويب الماركات.
- فتح النموذج لا يزيل سياق القائمة.
- بعد الحفظ، حدّث القائمة مع إبقاء البحث والفلتر المناسبين.

## 19. API ومصادر البيانات

| العملية | endpoint / query | التفاصيل |
|---|---|---|
| GET | /rest/v1/brands | select للحقول المطلوبة + products(count)، order=name.asc/desc، بحث الاسم/slug، فلتر is_active، Range للترقيم. استعلاما count إضافيان مستقلان عن البحث: كل الماركات والنشطة بـ `pageSize=1` لحساب بطاقات الإحصاء |
| POST | /rest/v1/brands | name, slug, logo, description؛ لا ترسل is_active |
| PATCH | /rest/v1/brands?id=eq.<id> | تعديل بيانات الماركة؛ تحديث الحالة في طلب مستقل بجسم is_active فقط |
| DELETE | /rest/v1/brands?id=eq.<id> | بعد التأكيد، وقيد FK هو الحَكَم |

### خريطة الأخطاء
- 409 أو 23505: قيمة مكررة (رسالة واحدة للاسم أو slug).
- 23503: الماركة مستخدمة؛ اعرض حوار الإيقاف بدلاً من الحذف.
- 401: انتهاء الجلسة.
- 403 أو 42501: لا صلاحية.
- انقطاع: مشكلة اتصال.
- غير ذلك: خطأ عام.
- لا تعتمد على message.contains('23505')؛ استخدم code/details من ApiException إن كان العقد يدعمهما، وإلا أضفهما إضافياً فقط مع اختبار وفق V1_SCOPE.
- كل التحويل عبر ExceptionMapper → Failure.messageKey → AppKey؛ لا تعرض نص الخادم الخام.

### التحقق
- اختبارات Repository تستخدم fake/mock لـ IApiClient وتغطي query/body/mapping/errors.
- لا اتصال فعلي بـ Supabase ولا طلب مفاتيح في هذه المهمة.
- تحقق الخدمة الفعلي يبقى يدوياً بحساب manage وحساب read-only، ويشمل GET/POST/PATCH/DELETE والبحث والفرز وRange وproducts(count)، ورفض RLS، وفشل DELETE لماركة مستخدمة.
- لا migration ولا RPC ولا dependency جديدة.
