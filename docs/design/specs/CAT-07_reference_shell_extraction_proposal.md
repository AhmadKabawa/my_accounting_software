# مقترح استخراج القشرة المشتركة للجداول المرجعية (D-DT-6)

## الهدف
تقليل تكرار واجهات CRUD للجداول الوصفية دون تحويلها إلى Map عام أو شاشة ديناميكية؛ يحتفظ كل جدول بكيانه typed، Draft، Query، Repository، Cubits، التحقق، الاختبارات، ومساراته.

## ما يمكن استخلاصه بعد اكتمال الأمثلة
- تركيب إطار القائمة (CrudListScreen وCrudListConfig وCrudDataSection) من إعداد typed صغير.
- حوار تحرير مشترك يضم الترتيب القياسي، dirty comparison بعد trim، مفتاح الحالة، وحفظ/إلغاء، مع field builders typed لكل feature.
- توحيد آليات ترجمة SQLSTATE (23503 / 23505 / 23514) ورسائلها، لا النص الخام من PostgREST.
- بنية اختبارات Repository/Cubit/Widget مشتركة تستقبل builders/fixtures typed وتُبقي الاختبارات الخاصة بكل feature صريحة.

## ما لا يُستخرج
- تعريفات الكيانات والمسودات والحقول وقواعد الفرادة والتصفية.
- ترتيب/فرز Query الخاص بالجدول، DTO، bodies وendpoint.
- الاعتماد على Map<String,Object?> أو reflection/schema discovery أو شاشة ديناميكية عامة.

## شرط البدء
لا يبدأ extraction إلا بعد أمثلة مستقلة مكتملة (sports وgenders وage_groups وmaterials وtags)، وبعد تحليل الفروق الفعلية وتحديد واجهة مشتركة لا تتطلب استثناءات كثيرة. عندها يختار استخراج تدريجي واختبارات عقد قبل إعادة نقل أي ميزة.

## خطوات مقترحة
1. توثيق مصفوفة التكرار والفروق في كل مثال.
2. تحديد أصغر contracts مشتركة للعرض/editor، مع فصل UI عن domain.
3. استخراج widget/helper واحد في كل commit مع الحفاظ على default behavior.
4. اختبار عقد لكل استخدام، ثم تحديث recipe وCORE_MAP إن كان الاستخراج Core.
5. مراجعة المعمارية قبل إعادة صياغة أي شاشة.
