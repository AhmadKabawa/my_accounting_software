## 1. نتيجة التدقيق

### 1.1 هل البنية Clean Architecture وهل الطبقات معزولة؟ — **نعم في الأساس، مع ملاحظات محددة**

الدليل من الكود الفعلي لميزة `catalog`:

| المحور | النتيجة |
|---|---|
| اتجاه الاعتماد | `domain` يستورد `dartz` وCore (Failure/UseCase/مفاتيح الأخطاء) فقط؛ لا Flutter ولا Dio. `data` لا يستورد `presentation`. `presentation` تستهلك UseCases عبر Cubit. سليم. |
| Repository/DataSource | الواجهة في domain وتنفيذها في data؛ DataSource يستخدم `IApiClient` المشترك وendpoint خاص بالميزة؛ تحويل الأخطاء عبر `ExceptionMapper` → `Failure` → `AppKey`. سليم ومطابق لـ ARCHITECTURE_RULES §6. |
| DI | `catalog_di.dart` ومسجَّل من `app_di.dart`؛ Cubits كـ factory. سليم. |
| الحالة | حالات `sealed` + `Equatable`، حارس آخر طلب يفوز، debounce داخل Cubit. سليم. |

### 1.2 جذور ضعف الواجهة (من الكود لا من الانطباع)

| العَرَض الذي ذكرتَه | السبب الجذري المثبت |
|---|---|
| لا padding صحيح / الواجهة ضيقة | **لا يوجد مكوّن إطار للصفحة أصلاً.** `ScreenEngine.maxContentWidth` معرَّفة ولا يستعملها أحد؛ `AppShell` يضع `navigationShell` بلا حشوة؛ `ListPageTemplate` يضع `Column` بلا حشوة أفقية. |
| سكرول للجدول فقط | `ListPageTemplate` = `Column` + `Expanded(dataTable)` وداخل `AppDataTable` `ListView` خاص به؛ الرأس والفلاتر ثابتة. |
| أزرار نصية للتعديل والحذف | `rowActionsBuilder` في Brands يبني `AppButton` نصياً داخل `Wrap`، و`AppIconButton` موجود لكنه غير مستخدم هنا. |
| حقل البحث ممتد بعرض الشاشة | `FilterBar` يضع `AppTextField` داخل `Expanded` في `Row` بلا حد أقصى. |
| الجدول قديم الشكل | رأس بخلفية `surfaceContainerHighest`، أعمدة `flex`، كثافة compact على المكتب، وعمود إجراءات بـ `flex: 1` ضيق يُقطّع الأزرار. |
| الكتالوج يفتح الماركات مباشرة | `catalog` branch يبدأ من `/catalog/master-data` الذي يعيد التوجيه إلى `/catalog/brands` (قرار D-01). |
| ضعف شريط التنقل على الهاتف | 3 وجهات فقط الآن؛ وعند التجاوز "المزيد" بـ `ListTile` خام داخل `showModalBottomSheet` خارج Core. لا مستوى ثانٍ (أقسام الوحدة). |
| لا صورة للماركة | قرار سابق: رابط URL فقط (الملاحظات §Deliberate boundaries). لا Storage ولا مُنتقي ملفات. |
| لم يحلل متطلباتي لتكون الواجهة غنية | `UI_UX_GUIDELINES` تفرض التحليل لكن لا شيء **يفرض تنفيذه آلياً** ولا قالب "غنى المعلومات" يُملأ قبل البناء (§5). |

## 5. كيف نجعل الذكاء الاصطناعي يبني واجهة قوية ولا يكتفي بواجهة ضعيفة

السبب الحالي أن القواعد **تصف** الجودة ولا **تفرضها**. العلاج بثلاث طبقات:

1. **قبل البناء — بوابة تحليل إلزامية:** Skill `screen-builder` يطلب ملء بطاقة قصيرة قبل أي كود: المهمة، من يقرأ/يكتب، **المعلومات التي تساعد القرار** (لا أعمدة قاعدة البيانات)، الإجراءات، الحالات، الأرقام الملخِّصة المبررة، ما يظهر على الهاتف. بلا بطاقة مكتملة لا بناء.
2. **أثناء البناء — لا ارتجال بصري:** كل صفحة قائمة تبدأ من `ListPageTemplate` (عبر `AppPageBody`)، والإجراءات من `AppRowActions`، والبحث من `FilterBar`. لا حشوات ولا `Expanded` ولا أرقام يدوية في الشاشة؛ إن نقص شيء يُضاف في Core أولاً (قاعدة فجوة الـ core القائمة).
3. **بعد البناء — بوابة جودة تعمل آلياً:** `ui_quality_test.dart` + مساعد `pumpScreenMatrix` يفحصان لكل شاشة: 4 عروض × RTL/LTR × فاتح/داكن، عدم وجود overflow، وجود تمرير واحد للصفحة، عدم وجود أزرار نصية في إجراءات الصف، عدم تجاوز عرض حقل البحث، وجود حالات التحميل/الفراغ/الخطأ. تُضاف إلى `flutter-ci.yml`.

يضاف إلى `AGENTS.md` بند "تعريف الإنجاز للواجهات" يحيل إلى `SCREEN_BUILD_PLAYBOOK.md` فقط (بلا نسخ القواعد، وفق ADR-0001 بند 8).
