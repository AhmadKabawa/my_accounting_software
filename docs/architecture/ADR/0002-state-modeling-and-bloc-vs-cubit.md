# ADR-0002: نمذجة الحالات واختيار Cubit أو Bloc وموضع freezed

- **الحالة:** معتمد
- **التاريخ:** 2026-11-08
- **الجهة صاحبة القرار:** مشرفو المشروع
- **النطاق:** إدارة الحالة في `features/` والتبعيات المرتبطة بها

## السياق

كانت حالات بعض الشاشات (`SplashState` و`OnBoardingState`) مولّدة بـ freezed، بينما حالات `HomeState` والـ cubits الأخرى `sealed` + `Equatable` أو enum. هذا خلط بين نمطين لغرض واحد، ويفرض `build_runner` وملفات مولّدة على نوع بسيط. ولم يكن واضحاً متى يُستعمل Bloc بدل Cubit.

## القرار

1. **Cubit هو الافتراضي.** يُستعمل Bloc فقط عندما تحتاج الشاشة تحكماً بالتزامن: `restartable()` (بحث/تصفية)، `droppable()` (تجاهل التكرار أثناء التنفيذ)، `sequential()` (ترتيب صارم). تُضاف `bloc_concurrency` لهذا الغرض.
2. **حالات Cubit/Bloc:** `sealed class` + `Equatable`، أو `final class` واحدة بـ Equatable عند وجود حالة بيانات واحدة. لا freezed للحالات، وحُذفت الملفات المولّدة لحالات splash وon_boarding (وأثره effect الخاص بـ on_boarding).
3. **freezed** يبقى في `pubspec.yaml` للكيانات الكبيرة في domain (مثل فاتورة) حيث تفيد `copyWith` والمساواة العميقة وfromJson. كيانات ونماذج auth الحالية مولّدة بـ freezed وتبقى كما هي.
4. اختبارات Cubit/Bloc بـ `bloc_test`؛ المستودعات fakes يدوية و`mocktail` للواجهات الصغيرة.

## النتائج

- نمط واحد للحالات يُقرأ دون توليد كود، وتغطية `build_runner` أصغر.
- قاعدة قرار مكتوبة لـ Cubit مقابل Bloc في [قالب الميزة](../FEATURE_TEMPLATE.md).
- المفاضلة: `Equatable` يتطلب كتابة `props` وcopyWith يدوياً للحالات ذات الحقول.

## التحقق

- لم تُشغَّل `flutter analyze` ولا الاختبارات في بيئة التنفيذ (لا Flutter SDK)؛ التغيير غير متحقق منه آلياً.
- لا يوجد اختبار معماري يمنع freezed في الحالات؛ القاعدة تُراجع يدوياً.
